# product_helper

Управление A/B-тестами, которые живут во флагах PostHog: с телефона или с ноутбука, без своего сервера.

Это одна статическая страница. Браузер сам ходит в API PostHog (CORS это разрешает), поэтому её можно положить на GitHub Pages и открывать с телефона.

## Что умеет

- **Флаги и эксперименты.** Все проекты PostHog, которые видит ключ. По каждому флагу показаны варианты, их доли, раскатка и привязанный эксперимент.
- **Доли.** Можно поменять доли вариантов и процент раскатки, нажать «Поровну», «Стоп» (контроль на 100%) или отдать варианту 100%.
  - Перед записью приложение показывает «было → станет» и предупреждения: изменение коснётся живых пользователей, вариант закэширован на устройствах, у флага идёт эксперимент.
  - Кнопка «Применить» включается, только когда вы ввели ключ флага.
  - Перед записью приложение заново читает флаг. Если его кто-то изменил, оно ничего не пишет.
- **Результаты по вариантам.** По каждому варианту приложение считает:
  - сессии или устройства;
  - покупателей, отдельно по каждому событию покупки;
  - конверсию;
  - выручку в USD по курсу дня покупки;
  - выручку на сессию или устройство;
  - байесовскую вероятность, что конверсия варианта выше контроля.

### Что даёт сверх раздела Experiments в PostHog

У Experiments есть статистика, калькулятор длительности, holdouts и запись сессий. Но он считает неверно для мобильного приложения, которое:

1. не шлёт `$feature_flag_called` — а Experiments считает экспозиции именно по этому событию;
2. меняет distinct_id каждую сессию — тогда «пользователи» в Experiments на самом деле сессии;
3. запоминает вариант на устройстве — тогда `$feature/<flag>` на событиях (живое значение флага) после смены долей расходится с тем, что видит пользователь;
4. пишет цены в местной валюте.

product_helper сам находит свойство, в котором приложение пишет свой вариант (например `<name>_variant`), и переводит цены в USD. Если в событиях есть `install_id`, он считает устройства. Если нет, считает сессии и показывает примерное число устройств: модель + версия ОС + страна.

## Ключ PostHog

Нужен Personal API key: PostHog → Settings → Personal API keys.

Права:

| Право | Уровень | Зачем |
|---|---|---|
| `feature_flag` | read, write | читать и менять доли |
| `experiment` | read | показывать эксперименты |
| `query` | read | считать результаты |
| `project` | read | список проектов |
| `organization` | read | список организаций |

Ограничьте ключ нужными проектами. Без `feature_flag: write` приложение будет только читать.

Ключ никогда не попадает в git:

- **На Mac** ключ лежит в `.env`. Файл указан в `.gitignore`, шаблон — `.env.example`.
- **На телефоне** ключ вводится один раз в настройках (⚙︎) и хранится только в localStorage этого браузера. Отправляется он только на `eu.posthog.com` или `us.posthog.com`: Content-Security-Policy страницы не пускает запросы на другие адреса.

## Запуск на Mac

Нужен Node 22+. Зависимостей нет, `npm install` не нужен.

Скопируйте ключ в PostHog и выполните команду. Она возьмёт ключ из буфера обмена, запишет его в `.env` с правами 600 и очистит буфер. Ключ не попадёт ни на экран, ни в историю shell.

```bash
cd ~/Projects/product_helper && k="$(pbpaste | tr -d '[:space:]')"; if [[ "$k" == phx_* ]]; then (umask 077; printf 'POSTHOG_PERSONAL_API_KEY=%s\nPOSTHOG_HOST=https://eu.posthog.com\n' "$k" > .env); printf '' | pbcopy; echo "Ключ записан в $PWD/.env, буфер очищен"; else echo "В буфере нет ключа phx_…"; fi; unset k
```

Затем:

```bash
node dev/serve.mjs
```

Откройте http://localhost:4600. Локальный сервер слушает только `127.0.0.1` и передаёт странице ключ из `.env`. Сам `.env` и другие файлы с точкой он не отдаёт.

Проверить ключ без браузера (выведет проекты и флаги, ключ не печатает):

```bash
node scripts/check.mjs <project_id>
```

Тесты:

```bash
node --test test/
```

Страница опубликована на GitHub Pages: https://resashkin.github.io/product_helper/

1. Откройте адрес в Safari.
2. Нажмите ⚙︎, вставьте ключ и выберите регион (EU).

localStorage общий для всех страниц `resashkin.github.io`. Сейчас на других страницах этого домена нет скриптов, поэтому прочитать ключ там некому. Если там появятся сторонние скрипты, product_helper стоит перенести на отдельный домен.

## Как считаются результаты

Запрос — HogQL через `POST /api/projects/:id/query/`. Тестовые аккаунты отсекает фильтр проекта, а события из TestFlight и симулятора отбрасываются (обе опции можно выключить).

1. **Единица подсчёта** — устройство (`install_id`), если оно есть в событии. Иначе это сессия (distinct_id).
2. **Вариант единицы** — первый вариант, с которым она встретилась в свойстве варианта. Единицы, которые видели два варианта, в таблицу не попадают. Их число показано отдельно.
3. **Покупатель** — единица, у которой есть хотя бы одно событие покупки. По умолчанию это события со словом «purchase», кроме попыток, отмен и ошибок.
4. **Выручка** — сумма `price`, переведённая из `currency` в USD функцией `convertCurrency` по курсу дня покупки.
5. **Вероятность победы** — апостериорное Beta по каждому варианту, 20 000 случайных выборок.
   - Априор у всех вариантов общий: средняя конверсия всех вариантов с весом 10 единиц.
   - Плоский Beta(1, 1) для этого не годится: он предполагает конверсию около 50%. При реальной конверсии в несколько процентов маленький вариант без единой покупки выглядел с ним «лучше контроля» с реальными покупками.
   - При малом числе покупок приложение предупреждает, что оценка ненадёжна.

Все настройки подсчёта, свойства и события можно поправить в «Настройки подсчёта». Они хранятся в браузере.
